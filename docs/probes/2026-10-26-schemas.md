# Candidate schemas for the frontier-model calls (26 October 2026, #73)

#70 left one question open: can a staged preflight keep provider cache reuse if every stage sends the same `response_format`? This round wrote candidate schemas for every call Muse Spark 1.3 answers (preflight stages 4–6, the in-loop escalation and the two stretch roles), tested them against Muse, and refined them from what came back.

**Answer: yes.** With one schema for the whole chain, stage 5 and stage 6 reused the 28k-token prefix in all three measured chains: two on contributor and the first one on Standard. The same-session control with the Day-1 per-stage schemas missed at stage 5, again. On Standard, the 3-stage chain cost **$0.063**, against the **$0.119** no-cache planning figure.

The probes also surfaced four properties of Muse's strict mode that change schema design (below). The frontier candidate produced a directive code can score in every answer (18 of 18). The Day-1 probe schema did so in 7 of 8, and its deadlines were inconsistent.

Code: `src/playtest/roles/` (contracts, prompts, validation; one Pydantic source per role) and `scripts/probes/probe_schemas.py` (phases `features`, `preflight`, `frontier`, `refine`, `stretch`). Raw calls stay local under `runs/probes/20261026T22*-schemas-*`.

## What Muse strict mode does with a schema

Measured in the `features` phase with tiny synthetic prompts (42 calls, $0.006).

| Finding | Evidence | Design rule |
|---|---|---|
| The schema is billed as prompt tokens, and `$ref`s are expanded first | A 200-value enum added 603 prompt tokens. A 300-value enum shared through `$defs` and the same enum repeated inline both cost 3,736 tokens; the second call hit the cache on the first's rendering | `$defs` saves nothing. Count every use of a large enum. |
| Object keys are emitted in **sorted order**, not schema order | Every answer came back alphabetized. Asked for a box (`h, kind, w`), the model wrote `kind` first, which only the circle branch (`kind, radius`) allows: a circle 4 of 4 times. Asked for a circle with the box branch listed first, it answered correctly 2 of 2 | No `anyOf` of objects; `strict.check` rejects them. Use one flat object, or nullable parts whose names sort in the order you want. |
| Every constraint tried is enforced while decoding, **by coercion** | `minLength: 20` turned "hi" into "hi..................", `maximum: 10` turned 500 into 10, `minItems: 4` invented three items, `pattern` turned "banana" into "h0" | A coerced value is a repair nobody sees. Provider schemas keep only `maxItems` (the model's own list, cut at the cap) and `pattern` (identifier spelling). Code checks other bounds after decoding, where a violation stays visible. |
| Limits | 10 nested objects accepted, 11 rejected. `oneOf` rejected. One enum of 1,001 values and two enums of 600 each were accepted, so the documented 1,000-value cap did not apply at these sizes | Keep below 10 levels. Large projects still need discovery caps; the enum limit is not measured past 1,200 values. |

`anyOf` with `null` works (`X | None`). An array of three rule kinds also decoded correctly when the prompt named each kind. Branch selection only fails when the model has not committed to a branch before the first sorted key, so flat objects are the safe default.

## Preflight stages 4–6

### The candidate

One schema, `StageAnswer`, serves every stage of a project's chain and every retry. It has three nullable parts, `stage_4`, `stage_5` and `stage_6`. A stage answer fills its own part and leaves the others null; stage `"all"` fills all three in one call.

- Readers are discovered field ids (an enum). Action inputs are discovered control ids (an enum). An action holds one to three controls together, so chords are possible; code never adds or removes one.
- Checks (preconditions, invariants, progress) name a reader by its **alias**, the key the decision model sees as `public.<alias>`. The first draft referenced field ids everywhere, which repeated the 224-id enum nine times and cost about 7,500 prompt tokens. With aliases, the v2 schema costs about 2,400.
- Invariants are one flat object: `kind` is range, monotonic or implies, and the fields a kind does not use must be null. A rule is something code can evaluate, not prose.
- Each part has its own gap list: `unobservable`, `uncontrollable` and `unjudgeable`. These map to the three kinds of gap the bible distinguishes.
- `review()` checks references and consistency: aliases exist, control types match axis values, checks are scoreable for the reader's type, and the stage scope is right. It returns exact problem strings, and `retry_turn()` sends them back. Nothing is repaired.

The stage-union candidate (one `anyOf` branch per stage) was dropped before the chain runs because of the sorted-key branch result above.

- **A byte-identical schema keeps reuse across stage transitions.** All 8 transition and retry calls hit in the three unified chains. The Day-1 control lost reuse at stage 5 (0) and kept only part of it at stage 6. That is the #70 result reproduced in the same session.
- **Cache misses still happen.** The Standard stage-4 control missed (0), yet stage 5 hit 28,017 a few seconds later. The two single-call `"all"` answers both reported 0, including an exact repeat 17 s later. Budget a chain as cacheable, not as cached.
- On Standard, stage 6 reused only the stage-4 prefix (28,017); on contributor it reused the whole stage-5 conversation. One chain cannot say whether that is the tier or chance.
- The contributor chains ran with the first stage-6 prompt; the Standard chain ran with the current (v4) prompts. That difference does not touch anything before the stage-6 instruction, which is the part that was cached.

### Semantic review of invariants (read against the FPSKit source)

The stage-6 content was judged by the orchestrator against the cited source lines. It is descriptive, not a benchmark (#24).

The first prompt produced checkable rules, and that made their problems visible:

- **Vacuous:** blend ranges [0, 1] restate a `Mathf.Clamp01` in the same method (`FirstPersonController` lines 296, 449, 516). So do non-negative timers and counters.
- **False:** "aiming ⇒ dash_blend == 0" fires while `m_Dash` decays after aim starts (line 513). "shooting ⇒ cooldown > 0.17" is backwards, because `m_TTL` resets to 0 on the shot (`BasicWeaponAttachment` line 105). "projectile TTL non-decreasing" fails on every pooled reuse (`RigidBodyProjectile.OnEnable` sets 0, line 76).
- **Progress:** timers, ages and activity counts were listed as progress in a game with no objective.

The stage-6 prompt was refined twice and compared on the **same recorded history** (stages 4–5 fixed, the stage-6 instruction varied, ABBA order):

| Stage-6 prompt | Runs | Rules | True and useful | Vacuous | False | Reads a method local | Progress listed |
|---|---:|---:|---:|---:|---:|---:|---|
| v2 (first) | 4 | 22 | 4 | 13 | 2 | 3 | 4 of 4, all timers or blends |
| v3 (+ transients, vacuity, progress is an objective counter) | 2 | 8 | 3 | 4 | 0 | 1 | 0 of 2, stated as unjudgeable |
| v4 (+ up-counting values are never negative) | 2 | 5 | 4 | 0 | 0 | 1 | 0 of 2 |

Rules judged true and useful:

- paused ⇒ movement unchanged and paused ⇒ aim_blend unchanged. `LateUpdate` returns at `if (Paused)` before every update (line 211).
- aiming ⇒ aim_blend > 0. The blend moves in the same frame (line 449).
- sliding ⇒ jump_count == 0. Sliding requires grounded, and landing resets the count in the same frame.
- sliding ⇒ forces changed: the slide adds to `m_Forces` every frame (line 336).

"Reads a method local" means the regex stand-in for stage-1 discovery captured a local variable (`shoot`, `dash`). Reflection-based discovery (#21) removes that. **v4 is the current prompt.** With n = 2 per prompt this is a direction, not an effect size.

## In-loop frontier

### The candidate

`FrontierAnswer` has the following parts. Muse emits them in sorted order.

- `hypotheses`: an id (an open one, or one the packet announces as new), statement, status, supporting and contradicting sequence numbers, confirm_if and refute_if. **An update is a delta:** cited sequence numbers add to the record, so earlier evidence is never dropped.
- `directive` (null keeps the current one): text; the hypothesis it `tests`; a target; an `expected` setpoint of manifest field, comparator, value and tolerance; and `deadline_s`, game seconds counted **from when S1 receives it**.
- `add_choices` and `prune_choices`: manifest actions and skills only, through an enum. Optional hold and axis overrides. They live as long as the directive does.
- `candidate_finding`: severity with a reason, expected and its source, actual, conditions, steps, evidence sequence numbers, and a `repro_check` setpoint for the reproduce skill. Code sets the finding's state.

The schema's enums are run-stable: manifest fields and action/skill names. Per-call references (sequence numbers, hypothesis ids) live in the packet, and `review()` checks them **per item**: a bad item is rejected with its reason and the rest of the answer stands.

### Against the Day-1 probe schema

Four synthetic scenario packets, interleaved, two runs each on contributor. The packets are shaped to the v0 bridge conventions from #14 and #19: per-sender bridge sequence numbers, and execution records with expected and observed effect.

| | Candidate | Day-1 probe schema |
|---|---|---|
| Schema-valid | 8 / 8 | 8 / 8 |
| Directive code can score | **8 / 8** (18 / 18 across every candidate call, Standard included) | 7 / 8: B#1 sent `changed` with value `"null"`, a string |
| Deadline meaning | `deadline_s` 10–30 s, always relative | `deadline_game_s` absolute in 7, relative in 1 (D#2: 8.0 at game_s 130.4) |
| Directive linked to a hypothesis | 8 / 8, every id valid | not representable |
| Candidate finding when the packet already shows a contradiction (A) | 2 / 2, each with `repro_check` | 0 / 2 |
| Latency, median | 5.7 s | 5.6 s |
| Visible output tokens, median | 410 | 318 |

The comparison used the first frontier prompt. The refinement calls and the Standard calls used the current one, which adds the hypothesis-delta rule and the core-choice note. The keys arrive alphabetically, so the directive is written before the hypotheses it tests. Every `tests` reference was still valid. The refinement round caught one malformed item: C#1 tried to add a "wait 0.5 s" by giving `move_forward` an `x` with no `y`. Review rejected that one add, and the answer's other parts stood. The current prompt says wait, escalate and finish are always S1's and are not manifest choices; the rerun added only `interact`.

**Cache across escalations.** An append-only conversation of three escalations (A, then C, then B) reused the whole earlier conversation: 2,673 and then 3,953 cached tokens. Fresh bodies were inconsistent. In run 1, the Day-1 schema's C and D reused the shared system, schema and manifest prefix (1,009 tokens), but the candidate's B, C and D reused nothing. In run 2, exact repeats reused 2,033–3,057 tokens. The two Standard calls reused nothing. An append-only conversation per run is the shape that measurably reuses.

**Standard.** The candidate answered A for $0.0087 in 10.4 s and C for $0.0066 in 6.5 s. Both were valid with no review problems.

## Contract gaps for the next issues

These are named here and not changed in this PR; each belongs to the issue in brackets.

- **`Finding`** has no field for `severity` with its reason, or for a reproduction predicate (`repro_check`), which the reproduce skill needs to evaluate a replay (#37, #38, #39).
- **`Directive`** has no link to the hypothesis it tests (#34, #35). Its `deadline_game_s` does not say whether it is absolute. The candidate converts a relative `deadline_s` to absolute game time from when S1 received the directive, and leaves it null when there is no game clock (#34).
- **Hypothesis records** with delta updates do not exist yet (#35).
- **Choice removal** with a reason is needed for pruned choices (#29).
- **Check semantics the checker must implement** (#34, #37):
  - `changed`/`unchanged` compare with the previous sample for a rule, and with the value at receipt for a directive.
  - An implies rule is evaluated per sample. `unchanged` in a then-check only counts across consecutive samples where the when-check held at both.
- **The manifest** must carry reader aliases with kinds, and an axis flag and maximum hold per action (#27). The frontier schema is built from those.

## Recommendation

- **#27 preflight:** use `roles.preflight.StageAnswer` as the one schema for every stage and retry, with the v4 prompts. Budget the chain at $0.063 per project when cached and $0.124 when not. Whether the single call (`"all"`, $0.047 projected) is good enough to replace the chain is a quality question for the bench.
- **#33 frontier:** use `roles.frontier.FrontierAnswer` with one schema per run, built from the manifest, and an append-only conversation per run. Apply `review()` per item, and never retry automatically in the loop: S1 decides whether to ask again.

## What this does not show

- Quality. Sample sizes are 1–4 per cell, the frontier packets are synthetic, and the invariant judgments are one reviewer's reading of the source.
- The cache mechanism. Byte-identical schemas reuse; changed ones did not. Why exact repeats sometimes miss is not isolated.
- Muse Wonder, real game frames or clips, and projects larger than 224 fields.
